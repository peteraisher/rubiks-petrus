# petrus

A very fast Rubik's cube solver that follows the
[Lars Petrus method](https://lar5.com/cube/), written in dependency-free Rust
with NEON SIMD on aarch64 (and a portable scalar fallback).

```
$ petrus -p short R U2 F\' L D2 B R\' U F2 D\' L2 B\' R2 U\' F L\' D B2 R F\'
  2x2x2  ( 5)  R2 U' D L2 F2
  2x2x3  ( 6)  U L B' L' B2 L'
  EO     ( 3)  L U2 L'
  F2L    ( 9)  U2 B' U' B U' B2 U' B' U2
  ZBLL   (11)  L' B2 L2 B2 L2 B' L2 B' L2 B L
  total 32 moves (HTM): R2 U' D L2 F2 U L B' L' B2 U2 L' U2 B' U' B U' B2 U' B' U2 L' B2 L2 B2 L2 B' L2 B' L2 B L
```

Steps are printed in the original frame; this solve was found with the
blocks on the left-back of a rotated view, so step 4 shows up as <U,B>
rather than <R,U>. Turns that cancel across step boundaries (`L'` `L` here)
are merged in the total.

| preset | what it does | mean length (HTM) | time / solve (1 core) |
|---|---|---|---|
| `classic` | Lars' 7 steps, fixed orientation, each step optimal | 51.5 | 0.5 µs |
| `fast` | steps 1-4 optimal, one-look optimal last layer (ZBLL) | 38.9 | 0.5 µs |
| `neutral` | as `fast`, best of all 48 orientations | 37.9 | 2.0 µs |
| `short` | beam search over orientations and step alternatives | 30.0 | 165 µs |
| `shortest` | wider beam | 28.2 | 736 µs |

Apple M1 Pro, random-state scrambles, best of 5 runs of 20 000 cubes
(`scripts/bench.sh`), with some background load. On all 10 cores the `fast`
preset does ~4.4 million solves per second. Tables are embedded at build
time, so there is no startup cost: a CLI solve takes a few milliseconds end
to end.

## The method

Petrus' steps, in the canonical frame the solver works in (every other
orientation is mapped onto it by symmetry, see below):

1. **2x2x2 block** at DBL (corner DBL, edges DL DB BL), any moves.
2. **Expand to 2x2x3** on D-L (+ corner DLF, edges DF FL), any moves.
3. **Fix the "bad" edges**: orient all edges for the F/B axis using
   <R,U,F,B>, restoring the block.
4. **Finish the first two layers** using only <R,U>, which is possible
   exactly because step 3 oriented the edges.
5. **Position the last-layer corners**, 6. **twist them**, 7. **position the
   edges** — all keeping the F2L and edge orientation intact.

Steps 5-7 can also be run as COLL + EPLL or as a single ZBLL (`--ll`).

### Switchable search behaviour

- **Greedy, fewest moves per step** (`classic`, `fast`): each step is solved
  optimally given the previous one. Nothing is searched beyond that.
- **Orientation neutrality** (`-o 1|24|48`): try the block in every
  location (24 rotations) and their mirror images.
- **Alternatives** (`-b` beam width, `-a` alternatives per step, `-s` slack):
  keep the best `b` partial solutions after each step, extending each with up
  to `a` solutions of up to optimum + `s` moves. This considers alternative
  step 1 and step 2 solutions jointly, and so on down the steps, without
  searching for a globally optimal Petrus solution.
- **Joint 2x2x3** (`-j`): solve steps 1+2 as one optimal 2x2x3 search.
- **Lookahead** (on in `short`/`shortest`, `--no-lookahead` to disable):
  rank partial solutions by moves so far plus a lower bound for the next
  step (exact for F2L and the last layer).

## Design

### State layout: one table lookup per move

Most solvers store "which piece is at each position". This one stores the
inverse: for each piece, a byte holding its position and orientation
(`pos + 12*ori` for edges, `pos + 8*ori` for corners), packed into two
16-byte vectors. Every lane then transforms independently under any move:
applying a turn (or a whole algorithm) is a 32-entry table lookup per lane,
which is exactly one `TBL` instruction per vector on aarch64
(`vqtbl2q_u8`). A face turn is two instructions; composing arbitrary
algorithms works the same way. This is the idea behind
[vcube](https://github.com/Voltara/vcube)'s `pshufb` representation, turned
around so that no shuffle-of-shuffle is needed. Edge orientation for all 12
edges falls out with two more `TBL`s and two horizontal adds.

Move tables and the 48 cube symmetries are not typed in: they are derived at
compile time (`const fn`) from 3D sticker geometry (`src/facelet.rs`), and a
test checks them against Kociemba's published tables.

### Pruning tables

Each step's heuristic is a max over small pattern databases built by BFS
(`src/tables.rs`):

- A table is indexed straight from the tracked lanes. Each lane's 24 possible
  values are first squeezed to the values reachable under the table's move
  set (e.g. 18 corner and 7 edge values under <R,U>), which shrinks the exact
  F2L table from 8 MB to 110 KB.
- Each digit table is pre-multiplied by its place value, so an index is a sum
  of independent L1 loads rather than a serial multiply chain.
- Distances are 4-bit nibbles.
- Tables are generated by `build.rs` and embedded with `include_bytes!`.
- Searches test tables one at a time, small cache-resident ones first, and
  stop at the first that prunes (most nodes are pruned).

The 2x2x3 is covered by four overlapping "2 corners + 3 edges" tables plus
the two 2x2x2s; the two that pair the expansion edges DF/FL with each end of
the block cut the step 2 search from 93 to 36 nodes.

### Search

Steps 1-4 are IDA* over canonical move sequences (no repeated face, opposite
faces in a fixed order), with alternatives collected in increasing length.
Steps 1 and 4 have exact tables, so they are effectively a table descent.

The beam expands partial solutions best-bound-first and stops when no
remaining partial can beat the beam's worst member, and caps each search at
the depth that could still enter the beam. So picking the best of 48
orientations costs 48 table lookups plus one search, not 48 searches.

### Compiled steps: one lookup per step

Once the earlier steps are done, a step's starting state is small: the
2x2x2 depends on 4 pieces (253 440 states), the expansion to 2x2x3 only on
DLF, DF and FL (6048 cases), EO only on the flips of the seven other edges
(64), F2L on 56 700 <R,U> states. So `build.rs` stores, for every case, the
solution the step search returns, and a step that wants one optimal solution
(every step of `classic` and `fast`, the greedy steps of `neutral`) is a
table lookup instead of a search (`src/compiled.rs`, 3.7 MB).

The solutions are exactly the search's: IDA* over canonical sequences
returns the lexicographically first optimal sequence in the step's move
order whatever its heuristic, since pruning with an admissible bound only
drops subtrees without a solution and none can reach the goal early. The
tables are built with any admissible bound (an exact descent for the 2x2x2
and F2L), and the tests check the embedded ones against a fresh build and
against the search, case by case. With one orientation and a beam of one,
the solve also skips the beam's bookkeeping. `fast` went from 2.4 to 0.5 µs
with identical output; the beam presets, which want several alternatives
per step, still search.

### Last layer: an optimal table for every case

After step 4 there are exactly 7776 last-layer states. `petrus gen-ll`
computes a move-optimal algorithm for every one (114 KB, `data/ll.bin`): it
enumerates "core" sequences (no U turn at either end) that preserve the F2L
and edge orientation, by increasing length, pruned with F2L/EO tables, then
wraps them in AUFs. An entry of length L is certified optimal once all cores
of length L-1 have been seen. It took ~6 minutes on 10 cores (core depth 15).

Lars' steps 5, 6, 7 and COLL/EPLL come out of the same table as projections.
An algorithm that solves state Y solves the corner permutation (or all
corners) of every state sharing Y's corner permutation (or corners), so the
best step algorithm per projection key is the shortest entry with that key.

## Correctness

`cargo test --release` runs:

- **Model:** geometry-derived moves equal Kociemba's tables; face turns have
  order 4; SIMD state = scalar cubie model = facelet model over random
  sequences; superflip and other known orders; facelet round trips and
  invalid-input rejection; all 48 symmetries map moves correctly; the fast
  per-piece conjugation equals the facelet-level reference.
- **Tables:** embedded tables are byte-identical to a fresh BFS; reachable
  counts match combinatorics (e.g. 253 440 for a 2x2x2, 56 700 for <R,U> F2L);
  2x2x2 God's number is 8.
- **Optimality:** each step's solution length equals an exhaustive
  heuristic-free search on near-solved states.
- **Compiled steps:** the embedded tables are byte-identical to a fresh
  build; every expansion and EO case, and the 2x2x2 and F2L of states met
  while solving random cubes, give exactly the search's solution.
- **Last layer:** all 7776 entries solve their case, and every LL mode
  satisfies its step postconditions without breaking F2L/EO.
- **Full solves** for every preset and mode: the solution solves the cube;
  each step reaches its goal in the solve's frame; EO uses only <R,U,F,B>
  and F2L only <R,U>; wider options never give a longer solution.
- **Portability:** the suite also passes on the scalar fallback
  (`--target x86_64-apple-darwin`, run under Rosetta).
- **Lint:** clippy, and `tests/lint_magic_numbers.rs`, which rejects integer
  literals above 2 outside `const`/`static`/`type` items (clippy has no such
  lint).

## Performance work

Profiled with macOS `sample` on long benchmark runs, plus
`examples/stepstats.rs` for per-step nodes and nanoseconds. The full log,
including the experiments that did not pay off (software prefetch, in-search
lookahead pruning), is in [docs/experiments.md](docs/experiments.md). The
main steps for the `fast` preset:

| change | fast preset, µs/solve |
|---|---|
| first working version | 5.8 |
| no heap allocation in the solve path, const-generic tables | 2.8 |
| compact nibble tables, pre-weighted indices (big multicore gain) | 3.3 (1 core) / 2.1M solves/s (10 cores) |
| short-circuit table tests, two extra 2x2x3 tables | 2.4 |
| compiled steps (one lookup per step, same solutions), no beam bookkeeping for one partial | 0.5 (1 core) / 4.4M solves/s (10 cores) |

The beam presets gained more from algorithmic changes: bound-ordered
expansion took `neutral` from 17.8 to 3.5 µs and `short` (old settings) from
155 to 45 µs.

## Comparison with other solvers

`compare/` (a separate crate, so petrus itself has no dependencies) solves
the same 1000 random states, one thread, same machine:

| solver | approach | mean length (HTM) | time / solve |
|---|---|---|---|
| petrus `fast` | Petrus, optimal steps + ZBLL | 39.0 | 0.5 µs |
| petrus `neutral` | + best of 48 orientations | 38.1 | 2.3 µs |
| petrus `short` | + beam search | 30.2 | 163 µs |
| petrus `shortest` | + wider beam | 28.3 | 722 µs |
| [thistle](thistle/) `fast` (this repo)* | Thistlethwaite, phases as table lookups | 31.0 | 0.2 µs |
| thistle `fast6`* | six phases, every table in L2 | 38.2 | 0.2 µs |
| thistle `short`* | + beam over starts and stored alternatives | 25.6 | 1.1 µs |
| thistle `shorter`* | wider beam | 24.1 | 2.3 µs |
| thistle `shortest`* | widest beam | 22.7 | 10 µs |
| [min2phase](https://crates.io/crates/min2phase) 0.2.4, target 21 | Kociemba two-phase | 20.6 | 700 µs |
| min2phase, target 23 / 25 | two-phase, looser target | 21.3 | 520 µs |
| [HARCS-C](https://github.com/xmdi/HARCS-C) `Petrus.harcs` | method solver (C), first three steps only | 24.1 to F2L | 367 µs |
| [rcuber](https://crates.io/crates/rcuber) 0.7.20 CFOP | method solver | 65.9 | 2.5 ms |
| rcuber Roux | method solver | 47.4 | 25.6 ms |

\* measured in a separate run under background load; interleaved in one
process with petrus as it is now, thistle `fast` takes 147 ns against
petrus `fast`'s 435, and thistle `shorter` 2.3 µs against petrus
`neutral`'s 1.9 (see its README).

Against other method-based solvers, the actual peers, petrus is roughly
700x (HARCS) to 50 000x (rcuber Roux) faster and gives shorter solutions in
every mode. HARCS-C is the C rewrite of
[HARCS](https://www.speedsolving.com/threads/harcs-jarcs-replacement-cube-solver.63241/),
the best-known general method solver. Its Petrus method file stops after F2L
(2x2x3 in one step, EO, F2L: 24.1 moves, against 27.0 for petrus `fast`
at the same point), so its time excludes a last layer; petrus spends ~30 ns
there. It is timed with `compare/harcs` (2000 of its own random states, one
thread, its search loop unchanged), which fetches a pinned commit and fixes
one upstream bug: a 32-bit shift that corrupts move sequences longer than six
moves.

Two-phase is not bound to a human method, so it wins on length: ~21 moves
in about half a millisecond, a floor that a looser target barely lowers.
petrus is ~1000x faster when ~39 moves will do, and its `shortest` preset
reaches 28 moves in similar time to two-phase's 21. Optimal solvers
(Korf/Rokicki style, e.g. vcube) are another regime entirely, taking
seconds per cube with gigabyte tables.

## A faster approach: thistle

[thistle/](thistle/) asks which method does best when every step is
optimised the same way. Every step of a method can be compiled into a table
of optimal algorithms per case; that is where petrus' compiled steps came
from. Compared that way, Thistlethwaite's four phases beat Petrus' five:
31 moves instead of 39, in under 150 ns per solve against 435 (one thread,
distinct cubes), with no branch in its chain that depends on the cube. With
a beam over 12 starting orientations and stored alternative algorithms it
gives 24 moves in about petrus `neutral`'s time. See its README for the
method comparison, the five- and six-phase variants, first-solve latency,
design and measurements.

## Usage

```
cargo build --release
target/release/petrus [OPTIONS] R U F2 D' ...      # solve a scramble
target/release/petrus -f UUUUUUUUURRR...           # 54-char facelets, URFDLB order
target/release/petrus -p short --random 5          # solve random states
target/release/petrus -p fast --bench 100000       # benchmark (all cores)
scripts/bench.sh                                   # best-of-N preset table
cargo run --release --example stepstats            # per-step cost breakdown
cargo run --release --manifest-path compare/Cargo.toml -- 1000
target/release/petrus gen-ll data/ll.bin           # regenerate the LL table
```

### Solve video

`video/` renders one scramble solved by petrus `fast`, min2phase, rcuber
CFOP and rcuber Roux side by side as an MP4. Each solver's moves play out
over its measured step times, slowed down and then sped up so every solver
finishes on screen:

```
video/export.sh                      # pick a typical scramble, measure, write JSON
(cd video/render && npm install && npm test && node render.mjs)
                                     # -> video/render/out/petrus-race.mp4
(cd video/render && node render.mjs --thumb)  # -> out/thumbnail.png for the post
```

The scramble is the candidate closest to every solver's mean length and
median time. Each solver's time is the median of single solves of the
scramble, each after 2 ms of solving other random cubes, so it is a
first-time solve: repeating one scramble back to back lets the branch
predictor learn a search (petrus' searches took ~1.4 µs instead of ~2.2
that way, before its steps were compiled). Timings use the published
crates unmodified; node counts come from a second build against copies
with a counter added (`video/count/vendor.sh`); petrus' compiled steps
count as one lookup each. `npm test` checks the renderer's cube model
against the Rust facelets after every Petrus step. Rendering needs
`ffmpeg` and Playwright's Chromium.

As a library: `petrus::solver::{Tables, solve, Options}`, with cubes from
`Cube::from_seq`, `Cube::from_facelets` or `Cube::random`.

## Limitations

- Half-turn metric only; no slice moves or rotations in output.
- On x86 the move application is scalar (correct, untuned); an SSSE3
  `pshufb` path would mirror the NEON one.
- The first solve after start-up page-faults the 22 MB of embedded tables
  (tens of milliseconds); steady-state numbers above exclude it.
